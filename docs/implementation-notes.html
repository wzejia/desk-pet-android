S8 UI 微调合集 — Implementation Notes

创建：2026-08-05 | 最后更新：2026-08-05（代码侧收口）

设计决策

S8-1：视觉回滚两层+横线，功能保留

决策：R3 单容器 → 两层独立 Surface + 层间 HorizontalDivider。
理由：用户视觉拍板优先于盲测口径（盲测组 2 三连败关账后，用户决定回滚两层布局）。
保留项：R3 功能修复（行高 48、FunctionBar padding 4dp、isUp 快照、idle 粉底 gate、停止键、上传链）全部保留——回滚的是视觉骨架，不是行为逻辑。
代价：单容器期的纵向空洞修复需在新两层骨架下手动验证不回归。

S8-3：cancelCurrentTurn 复用 + sealed 三层防线

决策：speaking/processing 态按住说话 → 复用 cancelCurrentTurn()（停 TTS + 停气泡 + 封轮 + 回 IDLE），再走正常 IDLE→LISTENING 采音。
理由：cancelCurrentTurn 已含完整清理逻辑（封轮 sealed、停 player、cancel pipelineJob、hide bubble），不重复实现。
sealed 三层防线：consumeSentences 循环头（L490）+ 合成后二查（L502）+ 多轮迁移（L464）——防止 cancel 后残跑协程继续合成/播放/迁移状态机。
已知局限：second-check sealed（L502）在单测中不可达——pipelineJob.cancel 关闭 sentences channel（CancellationException → sentences.close()），consumeSentences 自然退出。生产环境中 TTS 返回 Audio 时（非 cancel 路径）该守卫仍有价值。

S8-5：撤 reveal 音频同步，delta 直出气泡

决策：气泡文字改为直接消费 AG-UI delta 回调流式上屏，与 TTS 播放彻底解耦。
理由：用户拍板撤 KD13 "reveal 边念边出字"（2026-07-30 补选进，2026-08-05 拍板撤）。气泡文字应与 App 聊天页同节奏（delta→上屏），不等待 TTS 句级 PCM 时序。
退役范围：playAndReveal/reveal 方法删除；RevealScheduler 类保留备查（不删，万一后续需要恢复 reveal 时序）。
降级路径：TTS 单句失败 → 气泡文字不受影响（delta 已上屏），仅跳过本句播放。与旧版 "降级纯文字 4.5 字/秒 reveal" 语义不同——新版文字始终流式，不依赖 TTS 成功。

S8-6：pendingScrollMessageId 一次性事件（StateFlow 哨兵）

决策：悬浮窗「查看最近一轮」→ MainActivity intent → ChatViewModel.pendingScrollMessageId（哨兵 __last__）→ ChatScreen LaunchedEffect 消费。
选型理由：ChatViewModel 是 Activity 级 ViewModel（ViewModelProvider(this) 与 AppNavHost 内 viewModel() 命中同一 ViewModelStore），0 基建、0 跨边界透传。
替代方案（已否决）：Activity 持标志透传进 Compose 树——需加 @Composable 参数（污染 chat 域接口）或 CompositionLocal（新基建不划算）。
哨兵 sentinel 单测局限：requestScrollToLastRound/consumePendingScroll 是 AndroidViewModel private 方法，项目无 Robolectric/mock 基建，纯 JVM 不可达。降级为 P3 + 真机取证替代。

S8-7：wakeAckActive StateFlow gate 视觉映射

决策：唤醒路径（playWakeAck=true）置 _wakeAckActive=true，transition() 在 SPEAKING + wakeAckActive 时跳过通用 TALKING 映射，由 playPetOnceThen(JUMPING, WAITING) 接管。
理由：唤醒「我在」是 SPEAKING 态的子场景——需要明确的即时动作反馈（jumping→waiting），而非通用 TTS 播放的 TALKING 映射。
critic P2 修复：wozai 完时 _wakeAckActive.value = false 从条件块（if(isActive && state==SPEAKING)）移到 finally 块——onUtterance 抢跑切 PROCESSING 时原条件跳过复位致残留，下次 TTS SPEAKING 被误 gate。
两模式一致性：悬浮窗（PetOverlayService.playPetOnceThen）与全屏（FullscreenVoiceScreen LaunchedEffect 订阅 wakeAckActive）共用同一信号源，行为一致。

S8-8：TypingDots 替换 CircularProgressIndicator

决策：SENDING 状态显示三圆点错相呼吸动画（900ms 周期，三角波 alpha 0.3↔1.0），替换原 CircularProgressIndicator + "小朵思考中…" 文字。
理由：用户要求「三点打字指示」，对齐通用 chatbot 等候态范式。首 token 到达后状态机 SENDING→STREAMING 触发重组，TypingDots 自然消失（Compose 重组自动清理）。
与现有状态点对齐：仅替换 SENDING 分支，STREAMING（StreamingCursor ▍）、DONE（无指示）、ERROR（红色文字）不变。

设计偏差

S8-3 second-check sealed 守卫单测不可达

偏差：consumeSentences 循环内的 second-check sealed（L502）在单测中无法触发变异红。
根因：pipelineJob.cancel 关闭 sentences channel（CancellationException → sentences.close()），consumeSentences 在循环头 L490 的 sealed 检查前就因 channel 关闭而自然退出。second-check 在单测中永远不可达。
裁决：保留守卫（生产环境 TTS 返回 Audio 时仍有价值），记入已知局限，不删。

S8-6 sentinel 单测降级 P3

偏差：requestScrollToLastRound/consumePendingScroll 的 sentinel 单测无法在纯 JVM 编写。
根因：ChatViewModel 是 AndroidViewModel（构造需 Application），项目无 Robolectric/mock 基建（全量单测用 MockWebServer + fake 注入，不 mock 被测对象）。
裁决：用户拍板降级为 P3 + 真机取证替代。不引入 Robolectric 依赖（打破项目"零 mock 框架"纪律）。

S8-5 首轮 critic 死亡

偏差：S8-5 首轮 opus critic 子 agent 静默死亡（output 文件 0 bytes，TaskOutput "task not found"）。
根因：API 429 5 小时用量上限，子 agent 在请求中被截断，无错误传播。
处置：重派 critic（聚焦版，仅审查 delta 流式改动），成功返回。

结构重构执行 Phase 0（2026-10-10）

PetOverlayState 活性记账守卫的参数与语义定案

决策：心跳 30s / stale 窗 90s（3 周期容忍单次调度抖动）；isAlive = startedFlag 且 now−lastMark ≤ STALE_AFTER_MS（边界恰等判活）；running 收窄只读 val（写入只经 markStarted/markCleared——写入方契约显式化）；markHeartbeat 无条件记账、不写 startedFlag（复活防线由 isAlive 短路兜底，测试锚死）。
理由：service 活着时 isAlive 与原 running 同值（正常路径零变化）；心跳挂主线程 postDelayed（非唤醒式，doze 不打扰，30s 一次开销纳秒级）。
消费面：仅 SettingsScreen scale 滑条重启判定一处（全仓 grep 实证），stale-true 危害=误重启拉起悬浮窗，故守卫做轻不做重。

方法论：变异存活 = 不是真守卫 = 删

PetOverlayStateTest 变异 2a 实证：markHeartbeat 内 if (startedFlag) 守卫被删后测试仍全绿（存活）——isAlive 的 startedFlag 短路已完全覆盖其语义，该守卫是冗余防御，删除并把测试锚改指真实语义面（markHeartbeat 不得置 running，复活 bug 形态变异双红验证）。教训：变异锚验证不仅证明测试有效，还反向审计实现——存活变异处的「防御代码」多半是死防御，留着会误导读者以为有独立防线。变异存活的三种处置：删冗余守卫 / 修测试锚位 / 记录为已知等价防御（仅当有文档化理由）。

已知有界权衡：主线程卡死 >90s 时 isAlive 假阴性（Phase 0 评审定案）

心跳挂主线程 handler——service 活着但主线程卡死 >90s → isAlive 误 false → 设置页跳过一次 scale 重启。有界性：主线程卡 ≥90s 已近 ANR 区，旧码（running 布尔）在同样卡死下重启请求同样排队无法执行；后果限一次跳过、下次松手自愈。评审判定可接受，记录在案（Phase 0 独立评审 2026-10-10，4 条 P3 中唯一不修条目）。

S11 唤醒词准确率排查（2026-08-19 ~ 08-20）

根因链：三层独立叠加（阈值回归 / 云端分支丢失 / 门控碎裂时间轴）

决策：三层全部修复并上测试锚，非单点修补。
证据：docs/verification/v17-kws-accuracy/README.md（探针时间线、fed/gated 账目、10/10 验收日志）。
教训：①无测试锚的常量/分支在事故恢复的转录重放中静默丢失（阈值 0.5 回退 + 文字轮云端分支丢失双案， 对拍基线入 tracked 区）；②「第二声必中」类确定性模式是状态机/缓冲问题的指纹，不是检出率问题—— 编排层一度误判为音频延迟（单声等待实验表象），S11-6 探针数据证伪后才锁定门控语义。

S11-7：挂起窗 + gap-reset（超越桌面 parity 的增强）

决策：挂起窗 8 块=800ms（VAD 判停 800ms 同源依据）内低于门仍喂真实块（只消耗不续窗）； 连续低于门超窗 → 不喂 + sentinel 入队保序、reset 仅 decode 消费线程、幂等沿。
理由：流式 transducer 输入时间轴不可压缩；波束部分分需要尾随静音冲刷，不进流即冻结。
桌面核对：sidecar.py:184-197 同样只丢不补、无 gap-reset——parity 一致但语义不正确， 本修复属真机证据驱动增强（KDoc 已标注）。
代价：嘈杂环境每次过门事件增量喂 ≤8 块低能块（误触发风险有界，检出率日志可回收实证）。

S11-5：TextChatRouter 下沉（与原实现的两处有意偏差）

①原实现路由内联 runChat（jadx 取证），复原下沉为独立纯逻辑类——AndroidViewModel 内联代码 JVM 不可测， 正是上次无锚丢失的复败模式；代价=cloud↔chat 包级环（单模块可编译，留档）。②原实现仅云端路读 _messages.value，复原无条件读后传入（StateFlow.value 读无副作用，语义惰性等价）。 其余逐项与 jadx 寄存器伪码一致（critic 对拍过）。

S11-3：spike 真放行（08-04 空证据更正）

08-04 AEC spike「5.8min 零误触发」系空证据（旁路对 SPEAKING 恒 DROP 是 no-op，KWS 全程无音频输入）。 S11-3 真放行=spikeFeedKws 标志 + 有效性闸（观测期 fed 须在 SPEAKING 期间增长）。 UI 语义：导航离开≠disarm（spike 流程要求跨导航保持 arm），remember 初值读真态；disarm 配对点=按钮 toggle/进程死亡。
