# 唤醒必漏的调度级根因：解码线程被饿→时间轴撕裂；diff 水位计定位法

## Problem

2026-09-11 取证日：用户报四症状（唤醒失败/打断失败/应答延迟/说完被吞），逐环节代码审查
全部正常——门控参数对（gated 仅 0.05%）、路由对、阈值 0.3 历史验证过、引擎全天零 decode
error 零崩溃。真机实锤根因在调度层：**kws-decode 线程 MIN_PRIORITY（S25b 为治 UI 白屏
故意调低）在 CPU 争抢期被饿**——实测解码 7.5 块/s < 喂入 10 块/s，队列（64 封顶丢最旧）
恒满 → 音频时间轴被撕（累计丢弃 ≈940+283 块 ≈ 8.8s+2.8s）→ 唤醒词喂进解码器的是碎片，
transducer 打分必崩。现行样本：IDLE 态连喊 2 次不中（19:26:11/15，影子 0.15 中、主 0.3 不中）。

## 定位法（复用价值核心）

1. **diff 水位计**：`kws stats` 行自带 fed/decoded 累计，`diff = fed − decoded`。
   健康值 ≈0–64（队列容量内）；**持续增长 = 丢块进行中；恒定大值 = 历史累计丢弃 +
   常驻流水线**。分段读曲线：空闲期 diff≈0 而对话期暴涨 → CPU 争抢饿死（本案）；
   空闲期也涨 → 引擎/采麦层异常。修复前全天峰值 1757（≈17.6s 音频被撕）。
2. **影子对账二分**：影子引擎（0.15）与主引擎（0.3）喂同一音频——「影中主不中」
   把漏检从「声学问题」二分为「阈值问题或喂入问题」。本案 12 次影中 11 次主邻近
   也中（回声），排除声学失效，指向喂入质量。
3. **忙环负载注入**：`sh -c "while :; do :; done"` ×2 复现争抢（调度器级负载，
   零 UI 污染），修复前后同负载对照 diff——修复后忙环期 diff 稳定 0–1，一次定性。

## Fix（S35）

- 主引擎解码线程优先级 MIN(1)→**6**（ART nice≈-2，介于普通 0 与 UI -4 之间）；
  影子观测通道保持 MIN 不争抢（S34 教训：双引擎同权重=板子打满）。
- KwsCore 优先级参数化 + KwsCoreTest 优先级锚（变异锚：删赋值→红）。
- 装机双验收：忙环期 diff 0–1；Choreographer 零回归（S25b 白屏未复发）。

## Prevention

1. **「UI 流畅 vs 后台可靠」的优先级权衡不是免费的**：S25b 降 MIN 治白屏时，代价
   （对话期解码被饿→唤醒漏）延迟两周才在另一症状面爆发。调度优先级改动必须
   双向验收：改前行为（UI 帧）与改后受损面（解码吞吐）都要有可测锚。
2. **逐环节「都对」而系统失灵 = 查调度/时序/资源层**：参数、路由、异常全干净时，
   下一个嫌疑是线程优先级、锁竞争、队列丢弃这类不出现在任何单点日志的横切层。
3. **diff/fed/decoded 这类免费水位计要常读**：本案修复前数天的 stats 行里早已
   持续记录着丢块证据，没人看。
4. **单点日志全绿 ≠ 系统健康**：识别率结论必须配影子对账 + diff 水位 + 用户漏检
   报数三方交叉（见 CONCEPTS「时间轴撕裂」「影子回声」）。

## 反例

- 「引擎零崩溃、门控参数与对账表一致 → 唤醒链路健康」——本案修复前的真实状态
  恰恰是单点全绿而识别率受损。
- 「优先级调低无副作用，晚几毫秒无害」——对吞吐型消费者（流式解码）不成立：
  速率跟不上时队列丢弃是静默的，伤害走时间轴维度的另一条路径。
