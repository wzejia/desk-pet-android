# 内存优化归因与天花板分析（2026-10-11，承接 perf-retest）

> 问题：main 版复测空闲 TOTAL 217.1MB，较基线仅 −2.1MB，「提升不明显」。
> 本文回答：钱花哪了、还能不能压、各杠杆能压多少。
> 证据：smaps（su 0 拉取，userdebug 板）+ 冷启动 PSS 分时对照（`kws-load-timeline.txt`）+ APK 解包。

## 1. 为什么 Phase 3 提升小（结构性原因）

空闲 217.1MB 的构成（App Summary + smaps 同口径）：

| 分桶 | PSS | 占比 | 构成 |
|---|---|---|---|
| **Native Heap（scudo）** | **87.0MB** | 40% | ONNX 会话+模型 ~55MB（见 §2）+ 采麦/SSL/其余 |
| **Code（APK 常驻页为主）** | **92.1MB** | 42% | base.apk 页 76.8MB：**debug dex ~55MB 未压缩**（classes.dex 单文件 43.4MB）+ arm64 so 29.8MB（onnxruntime 21.7） |
| Java Heap | 18.7MB | 9% | Compose + 会话（已很瘦） |
| System/Other/Stack | 19.3MB | 9% | 系统服务摊派 |

**Phase 3 的优化全部作用在 Java 层行为**（logger 异步/列宽缓存/静止省绘/可取消）——作用面天花板
就是那 9%，且多为降低分配churn（GC 压力）而非常驻量。大头在 native + 代码页（82%），Phase 3
的手术刀根本没伸到那里 → −2~−6MB 是该层的合理产出，不是没做好。

## 2. Native 87MB 里是什么（冷启动分时对照，设备钟）

| 时刻 | NH | 事件 |
|---|---|---|
| 23:37:22 | 20.2MB | App 起、UI/overlay 就绪，**引擎未加载** |
| 23:37:23.5 | →63.7MB（t=5 65 档） | **主引擎 newFromAsset** + overlay/会话装配 |
| 23:37:31.8 | →86.0MB（t=7 86 档） | **影子引擎 newFromAsset**（S22 观测通道） |
| 23:37:39.7 | 86.0MB 稳态 | bootstrap 完成+采麦启动，此后 ±0.2MB 零漂移 |

- 引擎前基线 20.2MB → 稳态 86.0MB：voice 链原生成本 **+66MB**，其中模型权重仅 2×5.5=11MB
  → **ONNX 会话/运行时开销 ~45-50MB**（arena 型分配，加载后不还），其余为采麦/SSL/会话。
- **影子引擎段（t=6→t=10）+15MB = 单引擎完整增量**（模型 5.5 + 会话 ~9-10）——影子是纯观测
  通道（低阈值+MIN 优先级，只打日志），这是最干净的冗余。

## 3. 优化菜单（按性价比排序）

| # | 杠杆 | 天花板 | 证据强度 | 代价/风险 |
|---|---|---|---|---|
| 1 | **影子引擎退役**（或懒加载/开关化） | **−15MB** → 空闲 ~202MB | 强（分时对照实测单引擎增量） | 低：观测通道；若阈值观测还要，加 debug 开关即回 |
| 2 | R8 release 构建（`isMinifyEnabled=false`→true） | dex 55→~10-15MB → APK 常驻页 **−20~30MB** → TOTAL ~185-195MB | 中（dex 构成实measure，缩减率按同类工程估算，切后实测） | **分发形态决策**（debug 签名=SEC-1 已拍板维持，动 R8 须领导重拍板）；工程量小 |
| 3 | abiFilters 去掉 x86_64 | PSS ≈0 改善（x86 页本不常驻）；装包提速+省盘 31MB | 强 | 无风险，顺手 |
| 4 | 主+影子共享单引擎（若观测必须保留） | −9~10MB（省一份 ONNX 会话） | 中 | 中：线程安全面要验证（S34 教训=优先级冲突，共享是另一题） |
| 5 | 换更小 KWS 模型 | −2~4MB | 强 | **高风险：唤醒准确率红线**（S11 一声 10/10 来之不易），不建议 |
| 6 | Java 堆继续压 | <2MB | 强 | 性价比极低（Phase 3 已在此层） |

## 4. 结论（能优化到什么程度）

- **不动分发形态**：影子退役 + abi 清理 → 空闲 **~202MB（−7%）**，一天内可施工可验证。
- **叠加 R8（须领导拍板分发形态）**：**~185-195MB（−10~15%）**。
- **理论地板**：单引擎 + R8 + 不换模型 ≈ **180MB 上下**；更激进（换小模型）收益 2-4MB 但动
  唤醒准确率红线，不值得。
- 板子是 2GB 级 kiosk？系统层另算——本分析只管本 App PSS。
- 首帧 +20ms 与本案无关（另一观察项）。
